# KiwiGuide 评测报告

- 评测日期：2026-10-07
- 题集：`eval/questions.yaml`，30 题（中文 20、英文 10；simple 25、compound 3、underspecified 2）。标准答案尚待人工复核
- 对话模型和评判模型：`gpt-oss:120b-cloud`（同一个模型，见"局限"）。评测期间没有出现限流，未切换到备用模型
- 向量模型：`qwen3-embedding:0.6b`，稀疏模型：`Qdrant/bm25`
- 原始结果：`eval/results/` 下的 JSON 文件，每题包含检索到的页面、回答全文、两项评分及评判理由

## 1. 评测方法

| 指标 | 计算方式 |
|---|---|
| hit@k、MRR | 代码计算（`app/eval/metrics.py`）。排名以放进提示词的父块为单位，Agent 取合并后的 `retrieved`，与回答实际依据的资料一致 |
| 忠实度（1–5） | LLM 评判（`app/eval/judge.py`）：回答正文的事实性陈述能否在提供给模型的资料中找到依据 |
| 正确率（1–5） | LLM 评判：回答是否覆盖题目的 key_points，数字和条件必须一致 |

- 评判只看回答正文：来源列表、转介说明、免责声明是代码附加的固定文字，先去掉再评判
- 评判输出两次都无法解析时记为空，不计入平均分（本次 0 题出现）
- Agent 反问时，评测脚本用题目里预设的 `clarify_reply` 代为回答（没有预设时用"请按最常见的情况回答"），评的是反问之后的最终回答
- 运行命令：`uv run python scripts/run_eval.py --mode naive|agent [--top-k N] [--tag 名称]`，4 题并行

## 2. 结果对比

### 2.1 最终配置（top_k = 8，Agent 使用收紧后的反问条件）

| 指标 | 朴素 RAG | Agent |
|---|---|---|
| hit@1 | 0.833 | 0.800 |
| hit@3 | 0.967 | **1.000** |
| hit@5 | 0.967 | **1.000** |
| MRR | 0.894 | **0.900** |
| 忠实度 | 4.73 | **4.77** |
| 正确率 | **4.53** | 4.13 |
| 平均耗时（秒/题，4 题并行） | **8.5** | 19.6 |

按题型的正确率：

| 题型 | 题数 | 朴素 RAG | Agent |
|---|---|---|---|
| simple | 25 | 4.52 | 4.20 |
| compound | 3 | 4.33 | 3.67 |
| underspecified | 2 | 5.00 | 4.00 |

结果文件：`naive-answers-topk8.json`、`agent-answers-topk8-clarify.json`

### 2.2 结论
- **Agent 优于基线的指标**：hit@3 和 hit@5（1.000 对 0.967），MRR 略高，忠实度略高。基线唯一检索不到标准页面的 v05（"签证到期、新申请未批能否留下"）被 Agent 救回：改写为英文检索词并限定 visa 主题后，过渡签证（interim visa）页面排在第 2；原问题直接检索时 8 个结果都不在标准页面上。
- **Agent 不如基线的指标**：正确率低 0.40，且在三种题型上都偏低；耗时约为基线的 2.3 倍（多了改写和评估两次模型调用）。
- 忠实度两边都在 4.7 以上，差异在评分波动范围之内（见 2.4），不能据此说 Agent 更忠实。
- 结论：Agent 在"找到正确页面"和"缺信息时先反问"上有优势，但在本题集上"把要点答全"不如直接用原问题检索。主要原因见第 3 节。

### 2.3 调参前后对比（Agent）

| 配置 | hit@5 | MRR | 忠实度 | 正确率 | 反问题数 | 结果文件 |
|---|---|---|---|---|---|---|
| top_k 6（调整前） | 0.967 | 0.869 | 4.70 | 4.23 | 8 | `agent-answers.json` |
| top_k 8 | 0.967 | 0.899 | 4.60 | **4.37** | 11 | `agent-answers-topk8.json` |
| top_k 8 + 收紧反问条件 | **1.000** | **0.900** | **4.77** | 4.13 | **5** | `agent-answers-topk8-clarify.json` |

朴素 RAG 在 top_k 6 时：hit@5 0.967、MRR 0.894、忠实度 4.60、正确率 4.03（`naive-answers.json`）；top_k 8 时忠实度 4.73、正确率 4.53。两种方法在 top_k 从 6 调到 8 后正确率都上升，**最终采用 top_k = 8**。

**调整一：top_k 6 → 8**
- 原因：复合问题拆成 2–3 个子问题后，交替合并只给每个子问题留 2–3 个名额，同一页面的不同段落（如公共假日页面的"上班补偿"一节和"ACC 期间"一节）容易挤掉需要的那一段。
- 效果：Agent 的 MRR 0.869 → 0.899，正确率 4.23 → 4.37，复合题正确率 3.00 → 3.67；忠实度 4.70 → 4.60，变化在波动范围内。代价是提示词变长，平均耗时没有明显增加（27.6 → 25.0 秒，受云端波动影响更大）。

**调整二：收紧反问条件（`REWRITE_PROMPT`）**
- 原因：top_k 6 的运行中 30 题有 8 题反问，其中只有 t08、v07 是缺信息的题；另外 6 题本身已说明情况或只问一般规定，模型却追问了学历层次、家属、签证类型等提示词没有列出的信息。top_k 8 的运行里增加到 11 题。用户每被多问一次就多等一轮。
- 做法：明确"只有签证类型/学期和居住方式两类信息可以反问"，"问题已说明情况或问的是可分情况说明的一般规定时不反问"。
- 效果：反问降到 5 题，其中 v07 正确触发，另有 4 题（t03、e08、v05、c01）仍属不必要的反问；t08 这一次没有反问。另外在命令行对 t08 的问题单独测了 3 次，2 次反问；Day 5 演示用的"我住的地方要涨租了，我有什么权利？"测了 2 次，都反问。说明模型对反问的判断本身不稳定，收紧后误触发明显减少，但漏问的风险略有增加。
- 这次运行的正确率下降（4.37 → 4.13）主要来自 e03 和 e06 两题各得 1 分，与反问无关（这两题都没有反问），属于下面所说的生成和评判波动。

### 2.4 评分波动
同一道题在不同运行中的分数可能相差很大，例如 Agent 的 e03 三次运行正确率依次为 1、5、1，e06 依次为 5、4、1。原因有两个：生成回答的措辞每次不同；评判模型本身也有随机性。因此平均分的差异在 0.2 以内时不应视为有意义的差别。本次每个配置只运行了一次，没有做多次重复取平均。

## 3. 典型案例

### 成功案例
- **v05（检索救回）**：基线用中文原问题检索，前 8 个结果都不在标准页面上；Agent 把问题改写成英文检索词并限定 visa 主题，标准页面排在第 2。
- **t01（复合事实答全）**："押金最多多少、交给谁保管"。Agent 拆成"押金上限"和"押金交存"两个子问题分别检索，正确率 5；基线只答了押金上限，正确率 1–5 不等（两次运行分别为 1 和 5）。
- **v07（反问后作答）**："How many hours am I allowed to work?" Agent 先反问签证类型和是否在学期中，补充信息后回答学生签证学期中每周 25 小时。

### 失败案例
- **e03（找到页面、没找到那一段）**："公共假日上班怎么补偿？" Agent 检索到了公共假日页面，但放进上下文的是该页其他小节：调整前那次是"ACC 补偿期间"一节，回答说资料没有提到上班的补偿标准；最终配置那次是"可用性条款（availability clause）"一节，回答讲了雇主何时可以要求上班，没有讲补偿。两次正确率都是 1。基线用原问题检索，拿到的是"1.5 倍工资和调休"那一段。英文改写词偏向 public holidays 的泛称，没有带上 work on a public holiday 这类具体说法。
- **e06（回答自相矛盾）**：资料是对的（试用期页面），但 Agent 写成"试用期内不会失去任何权利……唯一的例外是不必遵循全部解雇程序"，评判认为它没有说明"不能提出不公解雇的个人申诉"并给 1 分。另一次运行中同一题得 5 分，说明问题在生成而不是检索。
- **v07 / e08（反问的代价）**：评判只看最终回答，看不到前面的反问。v07 的要点之一是"需要先了解签证类型"，Agent 实际上做到了，但最终回答里没有再提，被扣分。e08 在题目已经说明是 migrant worker 的情况下仍反问签证类型。
- **英文题正确率偏低**（Agent 3.90，基线 4.60）：英文题的检索词本来就是英文，改写带来的收益小，而拆分子问题后每个子问题分到的上下文更少。

## 4. 改进方向
1. **改写时保留原问题**：检索时把原问题和改写后的检索词各检索一次再融合，避免改写丢掉原问题里的具体说法（针对 e03）。
2. **按段落而不是按页面挑选上下文**：同一页面的多个父块被一起召回时，优先保留与问题更相关的段落，可以考虑加重排序模型（PLAN 中 Day 8 的选做项）。
3. **反问改为代码规则加模型判断**：签证类型、居住方式两类关键词可以先用代码检查问题和对话历史中是否已经出现，模型只在剩余情况下判断，减少误触发和漏问。
4. **评判时提供反问记录**：把反问和用户的补充信息一起交给评判模型，避免把"先反问"算作遗漏。
5. **多次运行取平均**：每个配置至少跑 3 次，报告平均值和波动范围；评判模型最好换成与回答模型不同的模型。

## 5. 局限
- 回答模型和评判模型是同一个模型，评判可能偏向自己的表述习惯。
- 题集只有 30 题，复合题和缺信息的题各只有 2–3 题，题型细分的数字只能作参考。
- key_points 尚未经过人工复核，个别题（如 e01 要求同时提到起步工资和培训工资）的要点比问题本身问得更多，两种方法在这类题上都只拿到 3 分。
- 每个配置只运行一次，没有统计波动范围。
