## 主要设计取舍
- **父子分块 + 混合检索**：小的子块用于匹配，大的父块放进上下文；稠密向量处理中文问题对英文页面的语义匹配，BM25 处理 bond、IRD 这类专有名词
- **先改写为英文检索词**：官方页面都是英文，Agent 把中文问题改写成英文检索词并按主题过滤，这是检索指标超过基线的主要原因
- **反问用 interrupt 实现**：会话在断点暂停并保存到 SQLite，用户回答后从断点继续，HTTP 和 MCP 两个入口共用这套机制
- **服务层与协议分离**：`ChatService` 承载全部业务逻辑，HTTP 接口和 MCP 服务都只做协议适配
- **测试不访问网络**：假模型和假检索器配合真实的 Agent 图，覆盖流程分支而不依赖模型输出

## 已知限制
- Agent 的正确率低于朴素 RAG：找到了正确页面，但放进上下文的常是同一页的其他小节，生成措辞也有波动（分析见 `docs/eval.md`）
- 每个评测配置只运行了一次，平均分 0.2 以内的差异不可靠
- Qdrant 本地库同一时间只允许一个进程打开，API 服务、MCP 服务和各脚本不能同时运行
- 安装 uv、Ollama 和登录 Ollama 的步骤没有在全新系统上重做；MCP 服务只用 SDK 客户端验证，没有在具体的桌面客户端里配置使用

## 后续可做
- 重排序模型：针对"找到正确页面但小节不对"的问题，对父块重新排序后再放进上下文，并重新评测
- Dockerfile：需要处理容器内访问宿主机 Ollama 的配置
- 评测多次运行取平均，降低结论的波动
